# 以现有台账为基础接入 MVU：研究与验证

日期：2026-10-24。版本：0.1.1，结构合并修复版。

## 结论

需要小手机等依赖既有表结构的功能时，应保留既有台账作为基础。MVU 转换不能仅生成自己的变量表后替换原台账，也不能只改字段名强行塞入既有表。

本次示例采用原 18 表在前、MVU 两张专用变量表在后，共 20 表。表数量随卡片变量结构变化，不应写死为所有卡都需要 20 表。

保留表结构与实现数据同步是两个阶段。当前候选修复完成结构合并与持久化验证，尚未实现所有重叠字段的自动同步，未进行真实模型填表准确率验证。

## 已发现并修复的结构问题

- 原 MVU 模板分组 1 为变量组、分组 2 为只读组；原 18 表分组 1 为角色组、2 为基础组、3 为不更新组。直接复制表会让基础组误用频率 0。
- 候选修复保留来源台账的分组编号、名称和频率，将冲突的 MVU 分组移动到空闲编号。
- 保留原 18 表的表 ID、列、规则、读取方式、世界书启用状态、关键词模式和插入位置。
- 明确记录 MVU 专用表 ID；重新转换时仅重建这些表的适配定义，避免把外部 18 表改为 MVU 原生规则或关闭其世界书。
- 合并只带表结构与规则，不带来源聊天记录。重复合并不清空已有目标记录。
- 新卡、模板条目和桥必须同时重生成。不能只导入一份 20 表 JSON，继续使用内置两表模板的旧转换卡。

## 字段映射策略（设计，尚未启用自动同步）

| MVU 数据 | 既有台账目标 | 必要条件 |
| --- | --- | --- |
| 当前地点 | 全局数据表的当前详细地点 | 精确值可共用，须规定单一更新来源 |
| 当前日期与时间 | 全局数据表当前时间 | 合成时间格式；缺失日期不得猜补 |
| 主角穿搭 | 在场角色表当前穿搭 | 先确认主角身份；不从一段穿搭文字猜出所有衣物子栏 |
| NPC 姓名 | 对应人物记录的姓名 | 真名与别名归并须有依据，不能仅同姓就合并 |
| 是否在场 | 在场角色记录的存在与状态 | 默认 false 不能当作已有角色离场的证据 |
| 明确的性别、身份、外貌、想法 | 已符合入表条件的人物档案/在场记录 | 保留重要角色筛选条件；不能把所有 NPC 自动塞入所有角色表 |
| 年龄 | 不直接写生日 | 年龄不能唯一确定生日 |
| 数值型颜值、个人资金、债务 | MVU 专用变量 | 保持类型与原卡校验；不伪造对应的台账业务字段 |
| 纪要、约定、关系里程碑、任务、技能 | 原台账对应表 | 沿用原规则，MVU 变量不能替代长期记忆 |

原 Schema 的默认值与已发生事实必须区分。没有证据的默认身份、想法、经历不能通过同步变成长期记忆。

## 同步方案要求

1. 每个重叠字段有明确的主要数据来源。不能两组模型独立改同一个事实，再由先后顺序决定结果。
2. 对可逆、无歧义的字段使用显式映射；自由文本、生日推导、人物重要性等不自动反向推断。
3. 只读映射视图优于重复存两份；如果小手机必须读取实体表，则在同一已验证写入批次更新镜像字段，并阻止填表器再次独立改写镜像。
4. 写入前验证原卡 Schema，再提交；不可先保存无效值、事后才悄悄修正。
5. 变更绑定聊天、角色和记录版本；跨设备或切换聊天后不提交旧结果。
6. 不为长期缓存把每轮动态内容前移；附加表与重复注入会增加 token，不能把此兼容方案当作缓存优化。

上述同步机制尚未全部实现。当前候选结构修复不能作为完整同步已经上线的证明。

## 验证

- 24 项适配器与合并测试通过。
- 使用台账 V1.147 实际存储引擎，验证用户当前 18 表与该卡两表合并。
- 验证原 18 表列、分组频率和世界书配置保留。
- 验证写入 MVU 日期后，基础表中的合成备忘记录仍在。
- 验证重载保留全部 20 表及两边测试值。
- 未写入用户真实聊天、未调用付费模型、未测试小手机的全部真实界面操作。

先补完共享字段与原 Schema 写入校验，再做实际卡片端到端验证；现有旧聊天不作为首次测试对象。
